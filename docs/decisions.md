| D-027 | **Mock subscription API** (`src/subscriptions/`): `GET /subscriptions/current`, `GET /subscriptions/history`, `POST /subscriptions/purchase {planId, transactionId, mockOutcome}`, `POST /subscriptions/change-plan {planId, transactionId, mockOutcome}`, `POST /subscriptions/cancel {requestId}`, `POST /subscriptions/resume {requestId}`, `POST /subscriptions/restore`, and mock provider notifications `POST /subscriptions/mock-notifications {eventId, type: RENEWED\|EXPIRED\|REFUNDED\|REVOKED, transactionId, periodStart?}`. | D-028 | **Lifecycle rules** live in a pure module (`lifecycle.ts`) with no I/O, applied atomically by `service.ts`:<br>• **Trial:** buying Basic when eligible starts a 3-day trial with 1,000 SUBSCRIPTION credits.<br>• **Conversion:** the first verified paid period, a `RENEWED` notification, expires the trial remainder and grants 3,000.<br>• **Renewal:** expires the remainder and grants the new allotment once. It never starts in the future, and the local clock alone never grants credits.<br>• **Upgrade:** effective immediately as a new paid period; expires the remainder and grants the full new allotment.<br>• **Downgrade:** only scheduled (`pending_plan_id`). It takes effect at the next renewal, and choosing the current plan again cancels it.<br>• **Cancel:** turns auto-renew off only; the entitlement and credits remain until the period end.<br>• **Expiry:** accepted only at or after the period end.<br>• **Refund/revoke:** of the current period ends the entitlement now and expires the remaining credits; of a past period it is recorded only.<br>Consumed credits are never clawed back, and balances never go negative. | PRD §2.1 and SUB-01…06. |
| D-029 | **Stale entitlement.** When the current period has ended and no newer verified period has arrived, its remaining SUBSCRIPTION credits expire (`PERIOD_ENDED`) on the next wallet read, spend, ad or lifecycle request. The status and analytics change only on provider events, so a late renewal still applies. | Subscription credits must not outlive their period (§2.1). "Derive effective state from authoritative state" (§4). |
| D-030 | **Ordering, duplicates and delays.**<br>• Each verified transaction is one immutable period, keyed by a unique `(provider, transaction_id)`.<br>• A renewal older than the current period is stored as `SUPERSEDED`, for audit only, with no credits.<br>• A renewal that arrives after its own period ended updates the state but grants nothing.<br>• An expiry that refers to an older transaction is ignored.<br>• A transaction redelivered under a new notification id is ignored before the rules run.<br>• A **REVOKED subscription can only be reactivated by a new purchase**: a DB trigger rejects any in-place reactivation, and renewals after revocation are ignored. | PRD §4 (late, duplicate and out-of-order notifications) and §2.4 (idempotency). |
| D-031 | **Concurrency.** Every lifecycle change, spend (now also in `POST /operations`) and ad reward takes the per-user lock first (`users` row, `FOR NO KEY UPDATE`), then the four bucket rows (`FOR UPDATE`), always in that order. Each lifecycle request's idempotency key is unique in `subscription_events`. | Concurrent lifecycle operations and deliveries (CR-03, ADS-04). |
| D-032 | **Rewarded ads.**<br>• **API:** `GET /ads/quota?action=` and `POST /ads/rewards {adEventId, action, mockOutcome: COMPLETED\|INCOMPLETE\|FAILED}`. A missing outcome counts as FAILED.<br>• **Eligibility:** the customer's available credits must be **insufficient for the stated action**. This applies to free, trial, expired and subscribed users alike, so there is no ad farm (open decision #5).<br>• **Reward:** a verified COMPLETED ad grants exactly 100 REWARD credits. INCOMPLETE and FAILED ads grant nothing and use no quota.<br>• **Daily limit:** 10 rewarded ads per UTC day of the server clock. The DB enforces it independently with `UNIQUE (user, utc_day, reward_slot)` and `CHECK (slot 1..10)`.<br>• **Responses:** an 11th ad → 429 `DAILY_AD_LIMIT_REACHED`; credits already sufficient → 409 `AD_NOT_ELIGIBLE`; duplicate `adEventId` → 200 replay with zero credit and zero quota.<br>• **Audit:** every attempt is an immutable row. | PRD §3.1, §3.2 and ADS-01…04. |
| D-033 | **Business clock.**<br>• **Business time:** periods, renewal and expiry checks, the ad UTC day and analytics `occurred_at` use an injected `Clock`.<br>• **Database time:** audit `created_at` and session expiry keep the DB clock.<br>• **Tests:** in-process tests inject a clock. The API harness starts a **second** server on the same disposable DB with `MONETALAB_TEST_CLOCK_FILE=<temp file>`; a serial spec rewrites that file, and `npm run e2e:server` can do the same with `E2E_TEST_CLOCK=1`.<br>• **Safeguards:** no HTTP route reads or changes time, a test checks the route table, and the clock file is refused with `NODE_ENV=production`. | "Controlled server/database time without public test-only HTTP backdoors." |
| D-034 | **Analytics events** go to the append-only `analytics_events` table, separate from accounting (nothing in money logic reads it). They are idempotent per (name, source key).<br>Events: `trial_started`, `trial_expired`, `subscription_started`, `subscription_renewed`, `subscription_cancelled`, `subscription_expired`, `subscription_refunded`, `subscription_upgraded`, `subscription_downgraded`, `reward_granted`.<br>Interpretations to confirm:<br>• `subscription_started` is emitted for a first paid period, including **trial conversion** (`fromTrial=true`) and resubscribe.<br>• `trial_expired` means a trial that ended **without** conversion.<br>• `subscription_downgraded` is emitted when the downgrade takes **effect**, not when it is requested.<br>• `subscription_cancelled` means auto-renew was turned off, which is distinct from expiry.<br>**No paywall event:** the PRD defines none, so none was invented. | PRD §4 event list. |
